# Журнал исследования SKILL.state

Последнее обновление: 2026-09-10 (дополнение к аудиту соответствия; исторические результаты ниже не переписаны)

[Дополнение к аудиту Paper](../experiments/PAPER-CONFORMANCE-20260910.md) разграничивает условия
720 запусков статьи, уточняет сохранность Σ и отделяет требование последнего наблюдения
от выбранного нами формата результата. [Аудит от 4 сентября](../experiments/PAPER-CONFORMANCE.md)
сохранён без изменений как описание первой основной серии.

Уточнение при подготовке статьи: прежняя метрика OpenCode `input + cache.read` не включала cache.write.
Пересчёт полного входа и влияние на проценты V3 описаны в [коррекции учёта токенов](./TOKEN-ACCOUNTING-CORRECTION.md).
Исторические таблицы ниже сохраняют исходное определение; новая серия использует полный вход.

Этот репозиторий исследует архитектуру из статьи
[SKILL.state: Scalable Long-Horizon Agent Skills](https://arxiv.org/abs/2608.26263): вместо повторной отправки модели
всего transcript исходный протокол передаёт неизменную постановку задачи `P`, полное структурированное состояние
`Sigma` и только последнее наблюдение `O`. Наш отдельный эксперимент v2 заменяет последнее окно на ограниченную
последовательность наблюдений. V3 сохраняет это окно, но принимает массив действий без ограничения по количеству и
выполняет его строго последовательно. Ядро заранее проверяет envelope, state и базовую форму действий;
полная проверка параметров вложенных tools не гарантируется до первого действия
([уточнение аудита](../experiments/PAPER-CONFORMANCE.md#validation-boundary-of-the-tested-v3-implementation)).

При проектировании также учитывался
[инженерный отчёт Apex](https://github.com/runapex/apex-router/blob/main/docs/DESIGN-skill-state.md): короткие задачи
могут не достигать точки окупаемости, фиксированный system/tool prompt иногда съедает экономию, а модель должна
выдавать patch, а не перезаписывать полный state.

## Что сравнивалось

В ранних основных A/B-прогонах одна и та же one-shot задача запускалась в двух независимых пустых рабочих каталогах:

- **Baseline** — штатный agent loop OpenCode или Codex с накоплением transcript.
- **SKILL.state V2** — модифицированное ядро, которое отправляет модели только `P + Sigma + O[n-k+1..n]` и принимает один
  обязательный `skill_step({state_patch, comment, action})` за provider turn.

Пять greenfield-проектов проверялись внешними black-box evaluators: `taskboard-cli`, `csv-insights`, `mini-template`,
`http-kv` и `dependency-planner`. Проверки не передавались в prompt и находились вне рабочей папки; само это расположение
не гарантирует запрет чтения во всех вариантах sandbox. Каждый исторический результат является
исследовательским `n=1`, если явно не указано обратное.

Важно: в исторических отчётах OpenCode prompt tokens считались как provider-reported `input + cache.read`, без
cache.write. Для полного входа нужна указанная выше коррекция. В отчётах Codex
`input_tokens` уже содержит cached input как подмножество, поэтому cache повторно не прибавляется. Абсолютные числа
между двумя harness нельзя сравнивать напрямую.

## Этап 1. Базовая OpenCode-адаптация: плагин

Первая версия была плагином поверх неизменённого OpenCode. Модель продолжала видеть обычные tools, а обновление state
было дополнительным необязательным вызовом. Постановка задачи также попадала в историю через чтение файла, а не
оставалась неизменной частью `P`.

На GLM-5.2 baseline набрал 32/40, а plugin state — 5/40. State использовал 6,696,188 prompt tokens против 3,318,537 у
baseline, то есть на 101.8% больше. Средний prompt на шаг действительно стал меньше, но модель сделала 289 шагов
против 79, почти не вызывала state tool и зацикливалась на повторном чтении спецификации.

Этот этап подтвердил только возможность ограничить provider-visible context. Он **не проверял контракт статьи**, потому
что runtime не мог обеспечить атомарность `state_patch + action`.

Подробности: [отчёт о plugin-прототипе](../experiments/skill-state/REPORT.md).

## Этап 2. OpenCode core v1: обязательный атомарный переход

Плагин был удалён, а протокол перенесён в ядро OpenCode. Модель получила единственный tool `skill_step`; полная
спецификация стала неизменной частью каждого запроса, patch валидировался до выполнения действия, а предыдущий
transcript сохранялся локально только для аудита.

Проверка request traces показала, что prompt действительно стал ограниченным: state-запросы оставались примерно
постоянного размера, тогда как baseline рос вместе с transcript. Но на коротких codegen-задачах GLM-5.2 резко увеличил
число действий, а Terra в первом полном прогоне повторяла успешные команды с пустым stdout. В результате:

- начальный GLM-прогон завершил только 9/10 cells; на трёх завершённых парах с одинаковым качеством state потребил на
  244.5% больше prompt tokens;
- полный Terra-прогон дал baseline 39/40 против state 38/40, а state использовал на 103.6% больше prompt tokens;
- один `csv-insights` state-run 74 раза подряд повторил `python3 -m py_compile main.py` и не вызвал `finish`.

Архитектура уже соответствовала центральному контракту статьи, но `O_i` содержал только результат действия. Для
успешной команды без stdout модель видела обезличенное сообщение и могла не понимать, какую именно проверку только что
выполнила.

Подробности: [отчёт OpenCode core](../experiments/skill-state/REPORT-core.md) и
[дизайн ядрового протокола](../experiments/skill-state/DESIGN-core-skill-state.md).

## Этап 3. OpenCode core v2: структурированные наблюдения, `k=3`

В улучшенной версии вместо одного результата передаётся окно последних трёх наблюдений. Каждое `O_i` содержит действие,
его input, необязательный модельный `comment`, итоговый status и result. Отдельное поле `verification` удалено из
долговременного state: недавняя проверка видна в `O`, а важный долгоживущий вывод модель переносит в `facts` или
`completed` своим следующим patch.

### GPT-5.6 Terra

Полный OpenCode A/B после этой доработки дал первый чистый положительный результат:

| Метрика | Baseline OpenCode | OpenCode SKILL.state v2 |
|---|---:|---:|
| Hidden checks | 37/40 | 39/40 |
| Provider turns | 52 | 33 |
| Prompt tokens | 1,063,814 | 426,310 |
| Изменение prompt tokens | — | **-59.9%** |
| Terminal `finish` | n/a | 5/5 |
| Rejected transitions | n/a | 0 |

State был дешевле на каждом из пяти проектов, не повторял одинаковые действия подряд и улучшил суммарное качество на
две проверки. Это `n=1`: предыдущий Terra-прогон на v1 был отрицательным, поэтому 59.9% нельзя считать ожидаемой
стабильной экономией.

### GLM-5.2

С тем же v2 и `k=3` GLM-5.2 остался ненадёжным. Baseline завершил 5/5 cells и набрал 39/40. State завершил 2/5,
получил частичные 31/40, 14 rejected transitions и три timeout. Сырой state-total был на 36.4% меньше по prompt tokens,
но это невалидная «экономия»: три реализации были принудительно остановлены незавершёнными.

Повтор с одним runner исключил высокую конкурентность как необходимую причину проблемы: длинные provider/model calls,
protocol violations и незавершение сохранились.

Подробности: [сводный OpenCode core-отчёт](../experiments/skill-state/REPORT-core.md),
[отдельный GLM-5.2 отчёт](../experiments/skill-state/REPORT-glm-5.2-k3.md) и
[сырой Terra `k=3` suite](../experiments/skill-state/results/20260903T124451Z/report.md).

## Этап 4. Codex core v2

Тот же контракт был перенесён в официальные исходники Codex: ядро восстанавливает `P + Sigma + O[n..n-k]`, сохраняет
полный rollout только для аудита и заставляет модель завершаться через `finish`. Базовый и state-бинарники собраны от
одного upstream commit. В каждом suite использовались medium reasoning, `k=3`, timeout 15 минут на cell и максимум два
одновременных runner.

| Модель | Pristine Codex | Codex SKILL.state v2 | Input tokens B/S | Изменение | Samples B/S | State timeout |
|---|---:|---:|---:|---:|---:|---:|
| GPT-5.6 Luna | 40/40 | 39/40 | 1,265,791 / 4,482,763 | +254.2% | 60 / 268 | 2 |
| GPT-5.6 Terra | 38/40 | 39/40 | 1,588,485 / 1,243,798 | **-21.7%** | 61 / 71 | 0 |
| GPT-5.6 Sol | 40/40 | 40/40 | 3,446,461 / 1,691,115 | **-50.9%** | 94 / 94 | 0 |

Luna подтвердила главный риск: меньший input на один запрос бесполезен, если строгий одношаговый loop увеличивает число
samples в 4.47 раза. Terra дала умеренную экономию с чуть лучшим качеством. Sol — самый чистый результат: одинаковые
40/40 и одинаковые 94 samples. Снижение input на 50.9% согласуется с эффектом меньшего provider-visible контекста и
точно не объясняется меньшим числом обращений, хотя trajectories и гранулярность tools между ветками различались.

При этом pristine Codex сохраняет Code Mode и может сделать больше работы за один provider sample, а state-ветка
использует только атомарные direct tools. Это сравнение двух практически работающих runtime, а не изолированный
prompt-only ablation с одинаковой гранулярностью tools.

Подробности:

- [дизайн Codex-реализации](../experiments/codex-skill-state/DESIGN.md);
- [отчёт GPT-5.6 Luna](../experiments/codex-skill-state/REPORT-gpt-5.6-luna-k3.md);
- [отчёт GPT-5.6 Terra](../experiments/codex-skill-state/REPORT-gpt-5.6-terra-k3.md);
- [отчёт GPT-5.6 Sol](../experiments/codex-skill-state/REPORT-gpt-5.6-sol-k3.md).

## Этап 5. Разделение original-paper и v2

После первых сравнений обе ядровые реализации получили отдельный режим исходного протокола статьи. В `paper` модель
видит строго `P + Sigma_n + O_n`, где `O_n` — только текст результата последнего действия, и отвечает envelope ровно
из `state_patch + action`. Здесь нет model-visible revision, `comment` и окна прошлых действий. Рекурсивный merge
поддерживает `null`-удаления, а reasoning и все более старые observations не возвращаются провайдеру.

Расширенный v2 сохранён отдельно для прямого сравнения: `state_revision + state_patch + comment? + action` и
структурированное окно `O[n..n-k]`. Для обоих режимов полный локальный transcript остаётся аудитным артефактом и не
является памятью модели. Реализация и команды запуска описаны в
[контракте original-paper mode](../experiments/PAPER-ORIGINAL.md). Результатов benchmark для paper-режима пока нет.

После объединения веток один бинарник каждого агента содержит все три пути. OpenCode выбирает их через
`OPENCODE_SKILL_STATE_MODE=baseline|paper|v2`, Codex — через `CODEX_SKILL_STATE_MODE=baseline|paper|v2`; без флага оба
запускают штатный baseline. Harness умеет собирать двух- и трёхрежимные suites, не меняя бинарник между cells.

## Этап 6. V3: последовательные батчи действий

V3 устраняет ограничение «одно действие на provider turn»: модель возвращает один patch, необязательный comment и
непустой `actions[]` без верхнего лимита. После предварительной валидации ядро применяет patch один раз и выполняет
массив строго по порядку; ошибка прекращает батч, а остаток фиксируется как `skipped`. В окне `k=3` весь батч с
результатами занимает один слот.

На OpenCode v3 сохранил существенную экономию против baseline, но уступил v2 и на Sol, и на Terra. На Codex/Sol v3
стал лучшим state-вариантом: 40/40, 818,113 input tokens против 990,678 у v2 (`-17.4%`). Codex/Terra почти не объединял
действия: 118 действий в 102 батчах, 39/40 и лишь `-2.1%` против baseline. Верхний лимит не понадобился: максимальные
батчи имели 5–7 действий.

Контракт, валидность прогонов, таблица по четырём runtime/model сочетаниям и ссылки на raw suites:
[отдельная запись v3](./V3-BATCHED-ACTIONS.md).

## Этап 7. Новая серия и техническая статья

Завершены 120 запусков после аудита Paper и исправлений: четыре режима на OpenCode/Codex и Sol/Terra,
плюс два дополнительных повтора Codex V2/V3. Подготовлены [техническая статья](../articles/skill-state-in-coding-agents.md)
и [короткий пост](../articles/linkedin-post.md). Это локальные материалы, не опубликованные автоматически.

OpenCode/Sol V2 дал 40/40 и −62,0% полного input к Native. Однако V3 не показала устойчивого выигрыша:
в сумме трёх попыток основной input оказался выше V2 на 4,0% у Sol и 4,6% у Terra, с одной дополнительной
непройденной проверкой у каждой модели. При добавлении input рецензента разрешений знак сравнения Sol меняется.
Поэтому основной цикл, вспомогательные вызовы и денежная стоимость не смешиваются.

Новая серия также выявила влияние инструкций рабочего хоста и различий упаковки ролей. Это инженерный пилот,
не clean-room воспроизведение и не причинная абляция. [Итоговый журнал](./ARTICLE-20260904.md) связывает результаты,
условия, исправления, оговорки и исходные артефакты. [Полный отчёт](../experiments/article-20260904/REPORT.md)
содержит все ячейки, включая неудачи.

## Отложенный эксперимент: LongCLI-Bench

Запланировано трёхрежимное сравнение Codex на 20 длинных задачах LongCLI-Bench: `baseline`, исходный `paper` и `v2`
с `k=3`, моделью GPT-5.6 Sol и high reasoning. Эксперимент пока не запускался. Требования к честному A/B/C, состав
задач, адаптация Docker harness, метрики, инфраструктурные ограничения и условия снятия с паузы зафиксированы в
[отдельной записке](./LONGCLI-BENCH-PLAN.md).

## План научного продолжения

Инженерный материал по [плану технической статьи](./TECHNICAL-ARTICLE-PLAN.md) подготовлен; ссылки — в этапе 7 выше.

2026-09-09 план существенно пересмотрен после повторов, удаления глобальных скиллов и серий с расширенными лимитами.
Теперь основной вопрос — когда компактная память экономит input, а когда потеря нужных подробностей добавляет
слишком много обращений к модели. В центре — отдельные абляции сохранённого input/result, метаданных и окна,
matched transcript и простой observation masking. Батчинг проверяется отдельно от ёмкости памяти.

720 запусков технической статьи остаются поисковыми результатами на пяти спецификациях, а не подтверждающей выборкой.
Для научной работы предусмотрены новые задачи, разделение development/test, сквозной аудит усечения, кластерная
статистика и поэтапный расчёт бюджета. Commit-aware buffer, retrieval и полная матрица на двух runtime перенесены
в необязательное продолжение. Новые эксперименты по этому плану не запускались.

Подробности: [план научного продолжения](./RESEARCH-ARTICLE-PLAN.md).

## Сводные выводы исторических пилотов

1. **Ядровый контракт реализован и проверяем.** В OpenCode и Codex модель владеет patch, runtime валидирует resulting
   state до action, а transcript не возвращается провайдеру.
2. **Ограничение prompt работает.** Размер state-запроса остаётся примерно постоянным, тогда как baseline transcript
   растёт. State в успешных запусках оставался мал — порядка 0.4–2.5 KiB.
3. **Главная переменная коротких задач — число шагов.** Один атомарный action на sample может проиграть штатному
   batching, даже если каждый отдельный prompt заметно меньше.
4. **Структурированное окно наблюдений устранило обнаруженный identical-action loop.** Однако оно не исправляет долгие
   model calls, невалидные payloads или неэффективную политику выбора разных действий.
5. **Результат сильно зависит от модели.** На одном Codex kernel Luna проиграла, Terra выиграла умеренно, а Sol
   сохранила идеальное качество и сократила input вдвое.
6. **Короткий codegen benchmark не проверяет асимптотику статьи.** Для центрального утверждения об `O(T)` против
   `O(T^2)` всё ещё нужны контролируемые сценарии на 25/50/100/200 шагов с одинаковым числом и гранулярностью действий.
7. **Batching помогает только при подходящей политике модели.** Неограниченный массив сам по себе не вызвал больших
   батчей; выигрыш появился, когда модель действительно группировала независимые действия и сокращала samples.
