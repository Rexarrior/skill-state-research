# Таймаут paper: повторное чтение с разными аргументами

Наблюдение после завершения HTTP-задачи в повторе 3, не вмешательство в запуск и не новый показатель качества.
[Исходный summary](../codex-skill-state/results/20260906T010746Z/skill-state-paper/http-kv/summary.json).

Сервис прошёл 9/9 внешних проверок, но агент не вызвал finish за 15 минут. В журнале 79 обращений,
71 успешный exec_command, 7 exec_command с ошибкой и один успешный apply_patch.
Метрика точных повторов показывает всего 1 повтор и максимальную серию 2.

При просмотре последних восьми результатов действий оказалось, что все восемь команд снова читают
server.py, test_server.py и/или README.md; меняются диапазоны sed, разделители команд и наличие rg.
Например:

```sh
sed -n '1,360p' server.py; sed -n '1,320p' test_server.py; sed -n '1,240p' README.md
sed -n '1,360p' server.py && sed -n '1,320p' test_server.py && sed -n '1,240p' README.md
sed -n '110,310p' server.py && sed -n '1,280p' test_server.py && sed -n '1,220p' README.md
```

Это наблюдаемое повторное перечитывание одних файлов с отличающимися аргументами. Равенство сериализованных
action/input почти не считает такие случаи. Поэтому низкое значение repeatedActions не доказывает отсутствие
повторяющегося поведения. При этом из данного примера нельзя установить причинный вклад отдельного поля state
или утверждать, что все 79 шагов были лишними. Не вводим постфактум эвристический порог и не переоцениваем баллы.

Для будущего контролируемого эксперимента можно заранее определить отдельную метрику повторного чтения
неизменившихся файлов, сохраняя различие между полезной повторной проверкой и отсутствием прогресса.
Сейчас исходы и все токены остаются в общей выборке; код, оценщик и условия не меняются.

## Дополнительная проверка обрезки

Все последние восемь результатов этого запуска имеют размер 4 126 байт и маркер обрезки.
В общем ядре MAX_RESULT_BYTES = 4 * 1024, после префикса добавляется маркер
«…[truncated by SKILL.state]». Лимит применяется к paper, V2 и отдельным действиям V3.
Он был заранее описан в [аудите соответствия статье](../PAPER-CONFORMANCE.md), это не новый лимит данной серии.

Таким образом, здесь одновременно наблюдаются повторные чтения и усечённые результаты. У paper доступен
один последний результат, у V2 — окно действий, у V3 — окно батчей. Одинаковый лимит одного результата
не означает одинаковый общий объём доступных свидетельств. Native использует штатную политику инструментов
и Code Mode, не этот SKILL.state-лимит. Его точная политика обрезки здесь отдельно не измерялась.

Из наблюдения нельзя заключить, что снятие лимита устранит таймауты: для этого нужна отдельная абляция
с заранее заданным бюджетом наблюдений. Скрипт truncation-audit.ts ретроспективно считает точный маркер
в сохранённых результатах всех state-режимов, не количество их повторных предъявлений модели.
Результат — truncation-audit.json; содержимое наблюдений не экспортируется повторно.

## Другой сценарий: поиск инструкций вместо разработки

В [HTTP-задаче paper, повтор 8](../codex-skill-state/results/20260906T020321Z/skill-state-paper/http-kv/summary.json)
таймаут наступил без созданных файлов: архив workspace пуст, оценщик не смог запустить сервер
и записал 0/9 с причиной `bad server banner`. Это не девять независимо обнаруженных дефектов сервера:
проверки функциональности не состоялись, поскольку реализации не было.

В начале агент несколько раз осматривал пустую рабочую папку, затем прочитал каталог скиллов и инструкции
профиля хоста. После этого он перешёл к широкому файловому поиску SKILL.md вне папки задачи.
В конце журнала видны повторные write_stdin с пустым вводом: агент ожидал поисковый процесс,
а не писал сервер. Исходный таймаут сохраняется в выборке; повторного запуска не было.

Этот случай отличается от перечитывания готового сервера выше. Он показывает конкретный путь влияния
профиля хоста, но не измеряет его причинный вклад во все результаты paper. Нормализованный текст стартового
профиля проверяется одинаковым для четырёх режимов; одинаковый текст не гарантирует одинаковую реакцию
агента на него. Для будущей чистой абляции нужен минимальный контролируемый профиль без личных инструкций.
